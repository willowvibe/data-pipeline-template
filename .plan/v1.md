# data-pipeline-template v1
Spec: docs/design.md (read it first; it is the source of truth for names, columns, tests and versions).
User request: "go with data-pipeline-template … option C (shop window now, kickoff tool later) … option B
(duckdb|postgres × none|airflow) … Open-Meteo … check similar repos and take whatever is usable …
write the complete implementation plan and other docs before scripting".
Conventions:
- Copier template: `copier.yml` at repo root, rendered tree under `template/` (`_subdirectory: template`).
  Conditional files use Copier's conditional names, e.g. `template/{% if orchestrator == 'airflow' %}airflow{% endif %}/`.
  Files needing Jinja end in `.jinja` (`_templates_suffix: .jinja`); everything else is copied verbatim.
- `scripts/render.sh <warehouse> <orchestrator> <dest>` (step 1) renders one combination non-interactively;
  `scripts/check.sh <warehouse> <orchestrator>` renders into a temp dir, creates a venv, `pip install -e '.[dev]'`
  and runs the generated project's `make ci`. Every generated-project step is checked through check.sh.
- Generated projects: Python 3.12, src layout `src/{{ package_name }}/`, deps pinned with `~=` to the versions in
  the spec, pytest offline by default (`PIPELINE_OFFLINE=1`), never call the network in tests.
- Compose command in Makefiles: `COMPOSE ?= $(shell docker compose version >/dev/null 2>&1 && echo "docker compose" || echo docker-compose)`.
- Host ports come from env with defaults: `WAREHOUSE_PORT` (default 5436), `AIRFLOW_PORT` (default 8080). In CI the
  Postgres service container listens on 5432 and the job sets `WAREHOUSE_PORT=5432`.
- Environment: there is NO `python` on PATH. Template tooling (copier, pytest, pytest-copie, pyyaml) is preinstalled in
  `/mnt/data2/git_repos/portfolio_projects/data-pipeline-template/.venv/bin` — use `/mnt/data2/git_repos/portfolio_projects/data-pipeline-template/.venv/bin/python` and `/mnt/data2/git_repos/portfolio_projects/data-pipeline-template/.venv/bin/copier`; scripts/render.sh must call `$COPIER` (default that path,
  falling back to `copier` on PATH for CI). Generated-project venvs are created with `python3.12 -m venv`.
- Python style: ruff (line length 100), type hints, small functions; no print() in library code (use logging).

## 3 warehouse layer and idempotent load
files: template/src/{{ package_name }}/warehouse.py.jinja, template/src/{{ package_name }}/load.py, template/tests/test_load.py, template/pyproject.toml.jinja, template/src/{{ package_name }}/config.py.jinja
do: Load raw JSON into `raw.hourly_weather`.
  - warehouse.py.jinja renders one implementation per `warehouse`: `connect()` context manager returning a DB-API
    connection (duckdb file `data/warehouse.duckdb` from env `DUCKDB_PATH`; or psycopg 3 using env
    `WAREHOUSE_HOST/PORT/DB/USER/PASSWORD`), and `ensure_schema(conn)` creating schema `raw` and table
    `raw.hourly_weather(city text, observed_at timestamp, temperature_c double precision, humidity_pct double precision,
    precipitation_mm double precision, wind_kmh double precision, loaded_at timestamp)`.
  - load.py: `load_file(conn, path) -> int` deletes rows for (city, date) then inserts that file's rows in one
    transaction; `load_all(data_dir) -> int` loads every raw file. Use only SQL that works on both DuckDB and Postgres
    (`%s` vs `?` placeholders handled in warehouse.py via a `PARAM` constant or helper).
  - Tests: loading the same file twice leaves the row count unchanged; a corrupt file raises and leaves earlier rows
    intact (rollback). Tests run against DuckDB for duckdb renders and against Postgres when `WAREHOUSE_HOST` is set
    (skip otherwise).
  - Generated deps: duckdb renders add `duckdb~=1.4` or the newest duckdb that dbt-duckdb 1.11 accepts (check
    dbt-duckdb's metadata; spec risk note); postgres renders add `psycopg[binary]~=3.3`.
